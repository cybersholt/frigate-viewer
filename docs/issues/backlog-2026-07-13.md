## 1. Channel-switch feedback (re-test before building)

**Symptom (reported):** changing channel, or toggling HD/SD, feels laggy — you tap, nothing happens,
then it switches.

**Re-measure before doing anything.** This was reported *before* `WebRtcCore` landed. Switching a
channel used to tear down and rebuild the entire WebRTC stack (factory + EGL context + audio module);
now only the `PeerConnection` is recreated, so a good part of that "waiting" may simply be gone.

**If it's still slow:** the fix is feedback, not speed — drive the loading state from the tap rather
than from the first stream event. `StreamContent` only shows the connecting overlay once the tile
reports `Connecting`, which is *after* the new session has been dialled.

## 4. Known telemetry gaps (RTSP)

Not bugs — limits of the transport, recorded so nobody re-investigates them:

- **Latency is unavailable on RTSP.** ExoPlayer's RTSP stack exposes no round-trip time; getting one
  means reading RTCP receiver reports directly.
- **Bandwidth may read "not reported by this transport" on RTSP.** media3's RTP data channels may never
  feed the `DefaultBandwidthMeter`. A real number needs a custom RTP data-channel wrapper that counts
  bytes. WebRTC tiles report real bandwidth either way.
- Stats cover **live tiles only**, not event playback.

## 5. Adaptive quality (idea — not yet a requested task)

The freeze watchdog *recovers* from a stalled picture (no frames for 8s → redial) but doesn't *prevent*
one. If 4K freezes keep recurring, the lever is dropping to the sub-stream automatically when frames
stall repeatedly, rather than redialling the same stream at the same quality.

Constraints already established, so they don't get rediscovered the hard way:
- The Exynos hardware decoder demotes to **software** on a `setOutputSurface` failure, and software 4K
  cannot keep up. `WebRtcLiveTile`'s zero-size layout guard is what stops that happening — **don't
  remove it.**
- **Wyze cameras cannot use RTSP at all** (their go2rtc SDP carries no `sprop-parameter-sets`), so any
  transport-switching logic must exempt them.

## From the 07-13 review: app bugs

### Fixed this session
- ~~Event-playback audio toggle shown on cameras with no audio~~ — **done.** `RecordingPlayer` now takes
  `audioEnabled`, sourced from `FrigateConfig.cameras[camera].audio.enabled` (the same flag the live tiles
  read), and hides the mute button when false.
- ~~Landscape fullscreen event playback: black status-bar icons on black letterbox~~ — **done.** Root cause was
  *not* a missing `isAppearanceLightStatusBars` sync: the live tiles avoid this by **hiding the system bars
  entirely** in fullscreen (`CamerasScreen.kt`), which event playback never did. `RecordingPlayer` now does the
  same via a `DisposableEffect` on `WindowInsetsControllerCompat`.

### Still open

**Snapshot-only cameras don't fit the event-playback model.** A camera configured for snapshots only (no
recording) shows a live tile fine, but the event flow assumes a clip/VOD exists. Before building anything,
look at how Frigate's own web UI presents review for snapshot-only cameras — this may be a "what does done
even mean" question rather than a bug. Related: an explicit live/snapshot mode toggle (see ideas below) may
be part of the right answer rather than a separate feature.

**Motion indicator dot is inconsistent across screens.** The camera tile's status dot cycles green (idle) →
red (recording) but never turns **blue** for motion, though blue means "motion" elsewhere in the app. The two
indicators need to share one source of state so a motion event reads the same everywhere.

**Event playback player chrome is off-spec.** Control buttons are misaligned (reproduced on the bird-feeder
camera), and the skin reads as a generic/legacy player rather than the app's Material 3 language. Cosmetic,
but it's the most-used screen after the grid.

**HA notification → event detail deep link.** *This is the one that matters — notifications come from Home
Assistant, not from this app's MQTT service.* The receiving half already works: `AndroidManifest.xml` declares
the `frigateviewer://` intent filter and `MainActivity.resolveDeepLink()` parses
`frigateviewer://event?id=<id>&camera=<cam>` (plus an extras fallback for HA's `intent://` wrapping). What's
missing is the HA-side config and a live end-to-end test. On the HA side this is the companion app's
`clickAction` on the notification, e.g.:

```yaml
data:
  clickAction: "frigateviewer://event?id={{ trigger.payload_json.after.id }}&camera={{ trigger.payload_json.after.camera }}"
```

Separately, the app's *own* `MqttForegroundService` notification cannot deep-link even in principle: it builds
an explicit `Intent(MainActivity)` carrying the extra `event_id`, while `resolveDeepLink()` reads a
`frigateviewer://` data URI or extras named `camera`/`id`. Key mismatch → resolves to `null` → default tab.
Either give it a proper data URI or rename the extra; decide first whether that path is even wanted, given HA
is the real sender.

### Gotcha: `reviewed` is a filter, not an include-flag

Verified live against the test server:

| query | result |
|---|---|
| `?after=…&before=…` (omitted) | 130 segments — 38 alerts + 92 detections |
| `?reviewed=1` | **2** segments (only the already-reviewed ones) |
| `?reviewed=0` | 128 segments (only the unreviewed) |

The OpenAPI blurb ("Include items that have been reviewed (0 or 1)") reads like an include-flag and is
actively misleading. Passing `reviewed=1` cost us a wrong feed showing 2 alerts / 0 detections. Omit it.

Corollary: `/api/review/summary`'s `last24Hours` returns `total_alert` / `total_detection` **and**
`reviewed_alert` / `reviewed_detection` — useful if a "N unreviewed" badge is ever wanted, but the feed's
own counts are derived from the loaded list, so summary isn't needed today.
