## 11. [Low/Medium] Event card shows a nonsensical duration ("170:44") — FIXED

**Root cause**: `formatEventTime()` in `EventsScreen.kt` computed the duration pill as raw
`String.format("%d:%02d", secs / 60, secs % 60)` — minutes never rolled into hours, so a 2h50m44s event
(10,244s) rendered as "170:44" instead of "2:50:44".

**Fix**: duration now branches on whether the event is >= 1 hour — `H:MM:SS` if so, `M:SS` otherwise (unchanged
for the common case).

**Verified on emulator**: Events grid still renders short durations correctly ("16:07", "0:05", "8:20", "21:24"
all still M:SS, no regression). Did not have a real >1h event on the test server to visually confirm the H:MM:SS
branch — verified by code inspection (straightforward integer division/modulo, same pattern used elsewhere in
the codebase for HH:MM:SS formatting).

## 12. [High, security debt] `TrustConfig.applyAllowUntrusted()` violates this repo's own "no trust-all-certs" rule

**Context**: found during the 2026-07-09 inspection-report triage. `TrustConfig.kt`'s `applyAllowUntrusted()`

at the time: leave as-is, log as known debt, don't touch it yet.

**Definition of done**: build the pinned-cert import UI (paste/import a PEM, store via
`CredentialStore.setPinnedCert`), verify a self-signed server can connect with it, *then* remove
`applyAllowUntrusted()` entirely.

## 13. [Medium, tech debt] `RunBlocking` in `FrigateClient.kt`'s session-cookie/client-construction path — RESOLVED

**This was the exact cause of issue #22** (the Events-screen ANR) — confirming the "check whether it's actually
bridging a synchronous OkHttp SPI" question below the hard way, via a live-reproduced ANR and bugreport stack
trace. Answer: `SessionCookieJar.ensureLoaded()`'s `runBlocking` legitimately bridges the synchronous
`CookieJar.loadForRequest`/`saveFromResponse` SPI, but was *also* reachable through `FrigateClient.hasSessionCookie()`
— a plain suspend call with no such protection, which could (and did) run on the main thread. Fixed by wrapping
that specific call in `withContext(Dispatchers.IO)`. See #22 for the full root-cause writeup and verification.

## 20. [Low, feature] Recording indicator dot should reflect active-event state — FIXED, verified on emulator

**Context**: from the fullscreen live-view redesign wishlist — the "● LIVE" dot in fullscreen chrome is a static

and pulsing red (`#25`'s recording-enabled). Verified live on the emulator: poll fires every ~15s while
fullscreen (confirmed via logcat), stops immediately on exit, no crashes. Not yet verified on the real Pixel 8

## 22. [High] Reproducible ANR on the Events screen — FIXED, verified on real Pixel 8

**Original hypothesis was wrong.** First seen while verifying fix #2 (the auto-refresh traffic loop); initially
suspected to be an artifact of heavy CPU load from the ADB automation used for that verification pass, since
plain logcat showed only "Input dispatching timed out" with no blocked-thread detail. A follow-up session
reproduced it live on the Pixel 8 (cold launch → tap Events → freeze, `Waited 5001-5005ms for MotionEvent`) and
pulled a full `adb bugreport`, which — unlike plain logcat — includes `/data/anr/anr_*` with the actual per-thread
Java stack trace. That made the real cause unambiguous:

```
"main" prio=5 tid=1 TimedWaiting
  at jdk.internal.misc.Unsafe.park(Native method)
  at kotlinx.coroutines.BlockingCoroutine.joinBlocking(Builders.kt:57)
  ...
  at net.triton.frigateviewer.core.network.SessionCookieJar.ensureLoaded(FrigateClient.kt:266)
  - locked <@addr=0x36acfa8> (a java.lang.Object)
  at net.triton.frigateviewer.core.network.SessionCookieJar.hasCookies(FrigateClient.kt:314)
  at net.triton.frigateviewer.core.network.FrigateClient.hasSessionCookie(FrigateClient.kt:86)
  at net.triton.frigateviewer.core.data.FrigateRepository.reloginIfNecessary(FrigateRepository.kt:60)
  ...
```

**Root cause**: `SessionCookieJar.ensureLoaded()` intentionally uses `runBlocking { credentialStore.cookies(...) }`
to bridge into `CredentialStore`'s suspend API — legitimate when reached through OkHttp's own synchronous
`CookieJar.loadForRequest`/`saveFromResponse` SPI (called from OkHttp's own background dispatch threads, per the
documented exception in `core/network/CLAUDE.md`). But `hasCookies()` is *also* called directly from
`FrigateClient.hasSessionCookie()`, which `FrigateRepository.reloginIfNecessary()` calls on **every** non-cached
API request — and that call chain runs on whatever dispatcher the caller's coroutine is on. Since ViewModels'
`viewModelScope.launch { }` defaults to `Dispatchers.Main.immediate` and nothing downstream switched off it, the
`runBlocking`-wrapped Keystore-backed cookie decrypt ran directly on the **main thread**.

**Why "all of a sudden" after the cookie code had been there a while — timeline, confirmed via `git log`:**
- **2026-07-09, commit `f81b95f`** ("implement per-server Frigate network client and WebRTC live view
  architecture") introduced both `SessionCookieJar` and `FrigateClient.hasSessionCookie()` together — this exact
  hazard (two different call paths into the same `runBlocking`-guarded `ensureLoaded()`, only one of them safe)
  has existed since day one of that architecture, not something newly broken this session.
- **2026-07-10, commit `0900678`** ("wire TokenRefreshAuthenticator and remove an unnecessary runBlocking") did a
  targeted review of this exact file for forbidden `runBlocking` usage per `core/network/CLAUDE.md`'s rule, and
  correctly removed a genuinely-unnecessary one in `buildClient()`. Its own commit message reasons about
  `SessionCookieJar`'s `runBlocking` too, concluding it's fine because it "bridge[s] a synchronous OkHttp SPI" —
  true for `loadForRequest`/`saveFromResponse`, but that review didn't separately notice `hasCookies()` is *also*
  reachable through `hasSessionCookie()`, a plain suspend call with no such protection. Half right, incomplete.
- **This session**: verifying the Wi-Fi and auto-refresh-traffic fixes involved an unusually large number of
  back-to-back `am force-stop` + cold-relaunch cycles on the same physical device in a short window (a dozen-plus
  across the whole session), plus concurrent CPU load from the ADB screenshot/tap automation itself. The
  main-thread block was very likely always there on a cold cache (freshly launched process, cookie not yet loaded
  into memory) — just normally fast enough (well under a second) not to be noticed. Repeated rapid Keystore-backed
  decrypts under real device load is a plausible trigger for crossing the 5-second ANR threshold specifically
  during this kind of intensive same-session testing, rather than in ordinary once-a-day app usage.

**Fix**: `FrigateClient.hasSessionCookie()` now wraps just the `hasCookies()` call in
`withContext(Dispatchers.IO)`, so the blocking decrypt always runs on the IO dispatcher's thread pool — the same
trade-off already accepted for `PerServerAuthInterceptor`'s legitimate `runBlocking` use — never on whatever
thread happened to call it. `SessionCookieJar`'s internal locking/loading logic is untouched.

**Verified on real Pixel 8**: 3 independent cold-start reproductions (force-stop → launch → tap Events
immediately) after installing the fix — all fully responsive, no ANR, confirmed via a fresh `adb logcat` sweep
showing zero `ANR in`/`Input dispatching timed out` entries across all three attempts.

This also closes the still-open tech-debt item #13 below (`RunBlocking` in `FrigateClient.kt`'s session-cookie
path) — it was this exact function, now fixed.
