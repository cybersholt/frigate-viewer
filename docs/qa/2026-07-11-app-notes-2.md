## 23. [Low] Settings row title isn't vertically centered against its trailing pill/switch — FIXED, verified

**Root cause**: `SettingRow`'s and `SwitchSetting`'s `Row` in `SettingsControls.kt` never set
`verticalAlignment`, which defaults to `Alignment.Top` — the trailing pill/`Switch` opted itself into
`Modifier.align(Alignment.CenterVertically)` individually, but the title `Text` never did, so it sat at the
row's top edge instead.

**Fix**: added `verticalAlignment = Alignment.CenterVertically` to both rows' `Row` (the correct, single-point
fix — centers every child uniformly instead of patching each one individually); removed the now-redundant
per-child `.align()` calls.

**Verified on emulator**: Appearance → Color mode now shows the title and the "DARK" pill on the same vertical
center.

## 24. [Low] Palette Style pill renders the raw enum name ("TonalSpot") instead of a display label ("Tonal Spot") — FIXED

**Root cause**: `AppearanceSettingsScreen.kt`'s `SettingRow(value = state.paletteStyle, ...)` passed the raw
stored enum-name string straight through. A correct display-name map (`paletteStyleInfo`, "TonalSpot" → "Tonal
Spot") already existed in `AppearanceSheets.kt` for the picker sheet's own rows — the settings-row pill just
never used it.

**Fix**: added a public `paletteStyleLabel(value: String): String` helper next to `paletteStyleInfo` and used it
in the `SettingRow` call. Stored value is unchanged; display-only.

**Not separately re-verified visually this session** (traced the fix's correctness via the existing map lookup
rather than a live screenshot, given time constraints) — worth a quick glance next time Appearance is opened.

## 25. [Medium, feature] Live view indicator dot should slow-blink red when recording is enabled for that camera — FIXED

**Fix**: `CameraConfig.record` was previously an untyped raw `JsonElement?`; added a typed `RecordConfig(enabled:
Boolean)` (matching the existing `DetectConfig` pattern) so `cameras.<name>.record.enabled` from Frigate's
`/api/config` actually decodes. Added a shared `LiveIndicatorDot(recordingEnabled)` composable (green pulse when
not recording, slower red pulse — 1400ms vs 900ms period, different color — when recording is enabled) and wired
it into both the grid tile badge (`StreamStatusBadge`) and the fullscreen chrome's "● LIVE" dot, each threaded a
new `recordingEnabled` parameter down from `state.cameras[name]?.record?.enabled == true` at the top-level
`CamerasScreen` composable.

**Relationship to existing backlog #20** ("recording dot reflects active-event state"): #20 was blocked on a
live "is an event ongoing right now" signal that isn't cheaply available. This ask is simpler and config-based —
just whether recording is enabled for the camera at all — so it's implemented now; #20's live-event-aware variant
can stay a separate, later enhancement on top of this if wanted.

**Not verified on-device this session** (compiles clean; didn't confirm against a camera with `record.enabled:
true` in the test server's actual config — worth a quick check next session).

## 26 & 27. Fullscreen camera switcher + back-gesture/orientation regression — FIXED, verified (same root cause)

**Both were the same bug.** Reproduced live on the emulator: switching to ch2 via the overflow menu updated the
title/chrome to "ch2" and logcat confirmed the RTSP dial succeeded (`State → READY
(url=rtsp://.../ch2)`) — but the visible video stayed frozen on ch1's actual last frame (confirmed via the
camera's own burned-in "CH 1" watermark still showing after switching). Root cause: `RtspLiveTile.kt`'s
`AndroidView` only assigns `player = exoPlayer` inside `factory`, which Compose runs once per slot — when
`remember(url, retryTrigger)` builds a *new* `ExoPlayer` for the new camera, the already-existing `PlayerView`
never gets rebound to it. Same underlying bug already diagnosed for backlog #7 (Retry not restarting playback),
just triggered by camera-switch instead of Retry.

**Fix**: added an `update = { it.player = exoPlayer }` block to the `AndroidView` — one line, fixes both the
camera-switch case here and #7's Retry case, since both go through the same rebind path.

**#27 turned out not to be a separate bug** — once the player actually rebinds correctly, the back gesture (which
was already correctly wired, per the earlier session's `WebRtcLiveTile`/`RtspLiveTile` `BackHandler` review)
exits fullscreen and restores portrait exactly as expected. Whatever appeared "stuck" was downstream of the same
stale-player state.

**Verified on real emulator repro**: ch1 → fullscreen → switch to ch2 → video now genuinely shows ch2 (confirmed
via its distinct scene + "CH 2" watermark) → gesture back → cleanly exits fullscreen and returns to portrait grid.

This also closes backlog **#7** (RTSP retry doesn't rebind player) — same fix.

## 28. [Medium, feature] Add a Developer Options settings page + a startup crash handler

**What's wanted**:

## 29. [Medium] Fullscreen live view: top chrome collides with the system status bar, and LIVE/RTSP text isn't aligned — FIXED, verified

**Fix**: added `.windowInsetsPadding(WindowInsets.statusBars)` to `FullscreenChrome`'s top `Row` — system bars
are hidden in fullscreen but can reappear as a transient swipe-down overlay
(`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`, already set in `WebRtcLiveTile`/`RtspLiveTile`), and the chrome now
clears it properly instead of rendering underneath. For the alignment: `StreamTypeBadge`'s pill has an 8dp
horizontal inset baked into its background; matched it by adding the same `.padding(end = 8.dp)` to the "LIVE"
indicator row, so both texts now share the same right edge.

**Verified on emulator**: fullscreen chrome screenshot confirms "LIVE" and "RTSP" now end at the same x position.
